# How this raft differs from etcd raft

This package is a fork of [etcd raft](https://github.com/etcd-io/raft)
(Apache License 2.0, see LICENSE). It is based on upstream's `main` branch
at commit `638f427` (2026-10-09), which holds every change of the latest
release, v3.7.0. This file lists every change in behaviour and why it was
made. Every modified file says so in its header, and each change is marked
"Fork" in a comment where it is made.

Most of these changes fix defects found in the upstream code by the
deterministic cluster simulator of [raftseg](https://github.com/raftseg/raftseg)
(`internal/raftsim`).
That simulator runs randomized clusters under message loss, duplication and
reordering; partitions; crashes that lose unsynced writes; configuration
changes; snapshots; leadership transfers; and reads. It checks raft's
safety and liveness properties as it goes. Each fix has a regression
test (in `fork_test.go`, `validate_test.go` or `raftpb/hostile_test.go`),
and each of those tests fails on the upstream code.

Raft tolerates crashes, not lies. A peer that lies about its log can break
safety, and nothing here changes that. What the fork adds is that a faulty,
outdated or misconfigured peer cannot crash a node with a malformed
message.

## History

The fork began at upstream's tag v3.6.0 and took two upstream fixes by
cherry-pick. It then merged upstream's `main` (mirrored in this
repository's `upstream-main` branch), so every fork commit and every
upstream commit stays in this repository's history.
Since v3.6.0, upstream:
- replaced github.com/gogo/protobuf with google.golang.org/protobuf, which
  made every message, and every field of a message, a pointer, read through
  getters (`m.GetTerm()`);
- requires Go 1.26 (it uses `new(expr)`);
- took the read-index fix this fork had cherry-picked, and other fixes
  (CHANGELOG/).

Each change below was ported to the new API, and each regression test still
fails on upstream's code.

## Dependencies

`raftpb` is upstream's protobuf code, generated by protoc-gen-go for
google.golang.org/protobuf, Google's protobuf runtime. It is this module's
only dependency:
- `raft.pb.go` is upstream's file with `go_package` (in the embedded
  descriptor and in `raft.proto`) naming this module.
  `TestGeneratedCode` builds protoc-gen-go from the required protobuf
  module and checks that it generates exactly this code from the
  descriptor, comments aside, so that the file holds no hand-written code.
- The tests use `internal/testutil` and `internal/datadriven` in place of
  testify and cockroachdb/datadriven, as before.
- `internal/depcheck` fails if `go.mod` requires anything but
  google.golang.org/protobuf, if `go.sum` lists anything but it and what
  its go.mod requires, or if any Go file imports, or any build compiles, a
  package outside the standard library, this module and protobuf.

The fork's earlier dependency-free `raftpb` (gogo's generated code with
the runtime removed) is gone with upstream's switch.

## Compatibility with v3.6

Upstream's switch keeps the wire format; this fork checks it against the
corpora it recorded from v3.6.0 (generators kept as `.go.txt` files next to
the data):
- `raftpb/testdata/golden.jsonl`: all 3,609 messages encoded by v3.6.0
  decode to what v3.6.0 said they held, and encode again byte for byte
  (`TestGoldenCompatibility`).
- `raftpb/testdata/malformed.jsonl.gz`, 21,654 damaged and hostile inputs
  (`TestMalformedAgainstOriginal`): 5,911 decode as v3.6.0 decoded them,
  apart from unknown fields, which protobuf keeps and gogo dropped; 15,047
  are rejected by both; 580 that v3.6.0 rejected now decode, each with
  unknown fields (protobuf keeps a field of the wrong wire type as an
  unknown field where gogo failed); and 116 that v3.6.0 accepted are now
  rejected as invalid wire format (field numbers above 2^29-1, varints
  longer than 64 bits, misplaced group markers), which gogo let through.
- `String()` now gives protobuf's text format, and encoding/json the
  struct's new shape, both as upstream has them; neither is compared.

## Safety

**Configuration changes known to be committed (`inferConfChangeCommit`).**
etcd raft applies a configuration when its entry is applied, not when it is
appended. Upstream's argument for why that is safe ("the old and new
configurations are guaranteed to overlap") holds only between consecutive
configurations. A node that held two configuration changes in its log, but
had not learned that the first was committed, still counted votes with the
configuration from before both. Configurations two steps apart need not
share a majority: going from (1 2 3 4) through a joint configuration to (1)
is enough. Such a node could be elected by a majority of the old
configuration while n1 led the new one. Two leaders in the same term then
committed different entries at the same index.

A leader appends a configuration change only after it has applied every
earlier one in its log. So when a later change follows a change in a node's
log, the earlier one is committed. The node now advances its commit index
to it, and it must apply that change before it may campaign. Its
configuration is then at most one step behind the latest.

The inference relies on raft refusing a configuration change while another
is pending, so it is skipped when `DisableConfChangeValidation` is set.
Test: `TestStaleConfigurationCannotElect`.

**Snapshots wait for entries being applied.** With `AsyncStorageWrites`, or
with `Node` when a snapshot arrives between `Ready` and `Advance`, a
follower restored a snapshot while committed entries were still with the
application. The application then called `ApplyConfChange` for older
configuration changes on top of the snapshot's configuration, which
corrupted it silently. A follower now refuses a snapshot until those
entries are applied, and the leader retries. Test:
`TestSnapshotWaitsForApplying`.

**`Ready.MustSync` covers snapshots.** Upstream left `MustSync` false for a
`Ready` that held only a snapshot and a new commit index. An application
that honoured it could acknowledge a snapshot, lose it in a crash, and
restart with an empty log. The leader's next heartbeat then panicked the
node. Test: `TestMustSyncSnapshot`. Upstream's data-driven scenarios that
show such a `Ready` now show `MustSync=true`: `confchange_v1_add_single`,
`confchange_v2_add_double_auto`, `confchange_v2_add_double_implicit`,
`confchange_v2_add_single_auto`, `confchange_v2_add_single_explicit`,
`confchange_v2_replace_leader`, `snapshot_succeed_via_app_resp` and
`snapshot_succeed_via_app_resp_behind` (in `testdata/`); that is their
only change.

## Linearizable reads

**A single voter answers reads only when it is that voter.** A leader that
had removed itself, leaving one voter, still answered reads from its own
state, because its configuration had a single voter. Test:
`TestReadIndexAfterLeaderRemovedItself`.

**A single voter waits for a commit in its own term.** Upstream answered a
single voter's reads at once, with a commit index that can lag behind
entries already acknowledged:
- after a restart, because the commit index is persisted lazily;
- after leadership has just been handed to it.

Such a leader now waits, as multi-voter leaders always did, until it has
committed an entry in its own term. Test: `TestSingleVoterReadAfterRestart`.

**Lease-based reads are backed by acknowledged heartbeat rounds
(`leaseValid`).** Upstream trusted CheckQuorum. CheckQuorum tests a
quorum's activity only once per election timeout, and it counts responses
to heartbeats sent at any time. As a result, a leader cut off from its
followers served lease reads for up to two election timeouts, while the
followers could elect a new leader and commit after one.

The lease now works as follows:
- Heartbeats carry a round number, and followers echo it.
- A leader serves a lease read only while a quorum of voters has
  acknowledged a round recent enough that each of them still refuses to
  vote for anyone else.
- Without such a quorum, the read is confirmed through a quorum, as with
  `ReadOnlySafe`.
- A leader gives up its lease once it has sent `MsgTimeoutNow`, because the
  recipient's election ignores leases.
- A node that restarts with a persisted term ignores vote requests for an
  election timeout (`startGuard`), to keep a promise it may have made before
  the restart.

Lease-based reads that fall back to a quorum use the same numbered
heartbeats, so the leader accepts read acknowledgements whatever its read
option (upstream accepts them only with `ReadOnlySafe`).

Tick rates must not drift apart by more than two ticks per election
timeout. Tests: `TestLeaseNeedsRecentRound`, `TestLeaseStartGuard`,
`TestNoLeaseReadAfterTimeoutNow`.

**Retried read requests (upstream fix, with a check added).** Upstream
fixed this after v3.6.0 (etcd-io/raft commits 9b9d6ee and 63903dd), which
this fork first cherry-picked and now has from upstream main. A leader
matched heartbeat responses to read requests by the request's own context.
A client that retried a read with the same context, while heartbeat
responses were delayed, could get its read confirmed by acknowledgements of
an earlier request: a leader already cut off from the cluster then answered
with a stale read index. Reads are now numbered by the leader, heartbeats
carry the latest number, and a read is confirmed once a quorum has
acknowledged a number at least as high.

As upstream wrote it, a heartbeat response whose context was not 8 bytes
long panicked the leader (`TestHostilePanicClasses` caught it). The fork
ignores such contexts, and positions beyond the reads registered so far,
which only a faulty peer sends. Tests: `TestReadOnlyDuplicateRequest`
(upstream's), `TestHeartbeatAckContextChecked`.

## Liveness

**A leader that leaves the voters hands over (`handOff`).** This was
upstream's own TODO. Upstream, a leader that removed itself either:
- stayed leader for good, dropping every proposal; or
- with `StepDownOnRemoval`, stepped down at once. It could then be the only
  node holding entries the voters needed, and it could neither campaign nor
  give them its vote. The group then had no leader permanently.

Now such a leader does the following:
- It keeps replicating and drops new proposals.
- It sends `MsgTimeoutNow` to the voter holding the most of its log, once
  that voter holds all of it, and retries every election timeout.
- It is exempt from CheckQuorum, and it confirms reads through a quorum.
- With `StepDownOnRemoval`, it steps down once it has sent `MsgTimeoutNow`.

Tests: `TestDemotedLeaderHandsOff`, and the updated scenarios
`testdata/confchange_v1_remove_leader.txt`,
`confchange_v1_remove_leader_stepdown.txt` and
`confchange_v2_replace_leader_stepdown.txt`.

**A transfer waits for pending configuration changes.** The
`MsgTimeoutNow` of a hand-off often arrives together with the commit of the
configuration change that prompted it, before the recipient has applied
that change. Upstream, the recipient dropped such a message, so the group
waited out a full election timeout. Now it campaigns as soon as the change
is applied. `TestDemotedLeaderHandsOff` requires the hand-off to complete
within a heartbeat.

**A node that is not a voter can campaign to hand its log over
(`mayRescue`).** A leader that removed or demoted itself can be deposed
before it hands over. It may hold entries no voter has, while voters that
have not applied its removal still count it, need its vote and cannot get
it. Such a node now campaigns through a pre-vote. The pre-vote wins only if
no voter hears from a leader and the node's log is at least as up to date
as theirs. Once elected, the node replicates its log and hands leadership
over. Votes are counted in its configuration, as for any candidate. Test:
`TestRemovedLeaderRescues`.

**Nodes answer a stale leader.** Without CheckQuorum or PreVote, upstream
relied on `MsgVote` to carry a higher term to a stale leader. But a node
sends `MsgVote` only to the voters of its own configuration, and a learner
sends none. A leader whose configuration needed such a node waited for it
indefinitely. A node now answers appends from a lower term with its own term,
as the Raft paper prescribes. Test: `TestAnswersStaleLeader`.

**A candidate behind in term learns the higher term.** Upstream ignored a
vote request from a lower term. A candidate whose term is behind a voter it
needs can then never win, unless something else tells it the higher term,
and nothing need. The simulator found a joint configuration (1)&&(6) in
which n1 campaigned for ever at terms below n6's, while n4, still on an
older configuration that excluded n1, kept raising n6's term with
campaigns of its own: no leader for good. A node that knows no leader now
rejects a vote request from a lower term with its term, as the Raft paper
prescribes. A node that knows a leader still ignores it, so that a removed
node does not learn the current term from a healthy cluster. Test:
`TestCandidateLearnsHigherTerm`.

**A node without a term no longer panics on a pre-vote.** Raft's storage
contract persists entries before the hard state, so a crash between the two
can leave a node with entries of a term but no term of its own (0). Such a
node rejects a pre-vote from a candidate with a shorter log, and upstream
answered with its term, 0, on which `send` panicked. The node now rejects
without answering; the candidate would have ignored a term-0 answer as
stale. The simulator found this once retried reads changed its schedules.
Test: `TestPreVoteRejectedWithoutTerm`.

**`MaxSizePerMsg` 0 no longer breaks application.** With
`MaxCommittedSizePerReady` left at its default (`MaxSizePerMsg`), a limit
of 0 caused one of two failures:
- the first `Ready` panicked; or
- application paused for good, because 0 >= 0.

A limit of 0 now applies one entry at a time. Test:
`TestApplyWithZeroSizeLimits`.

## Hostile and malformed input

**`ValidateMessage`.** `RawNode.Step` and `Node.Step` check every message
from a peer. A message from a peer is one with a sender other than the
node itself or its storage threads. The check rejects:
- local message types (including `MsgForgetLeader`), and types outside the
  enum;
- reserved or missing node IDs;
- local response lists;
- entries out of order, or from a term above the message's term;
- nil entries, and entries with fields this version does not know:
  protobuf keeps unknown fields, so they would be stored and replicated
  with the log without counting towards its size limits;
- proposals whose configuration change does not decode. Upstream, such a
  proposal panicked the leader.
- snapshots without metadata or configuration, or whose configuration raft
  would panic on;
- messages addressed to another node;
- a nil message.

A transport must set `From` to the authenticated sender, with one
exception. `MsgProp`, `MsgReadIndex` and `MsgTransferLeader` are forwarded
unchanged by followers, so their `From` is the node that made the request.
Tests: `TestValidateMessage`, `TestValidateMessagePointers`,
`TestStepValidates`, `TestUndecodableConfChangeDoesNotPanicLeader`,
`FuzzStepHostile`.

**Message types outside the enum.** protobuf decodes any int32 into an
enum field, and upstream's `IsLocalMsg` and `IsResponseMsg` indexed an
array with the type: a negative type in a message from a peer panicked
`RawNode.Step` before validation. Negative types are now neither local nor
responses, and validation rejects them. Found by `FuzzStepHostile` once it
stepped messages decoded from damaged bytes. Test:
`TestNegativeMessageType`.

**Forwarded requests are copies.** A follower passes proposals, reads and
transfer requests to its leader. Upstream readdressed the message given to
`Step`, which was harmless while messages were values but, now that they
are pointers, changed the caller's message under it, and a message that a
transport delivered twice arrived the second time addressed to the leader.
The follower now forwards a shallow copy (`forward`; the payload is shared,
not copied). Tests: `TestStepLeavesForwardedRequestsAlone`,
`TestShallowCopyCoversEveryField`.

**Bounded message nesting.** Decoding recurses once per level of
`Message.Responses`; without a bound, about 40 MB of crafted input (8
million levels) exhausted the goroutine stack, which Go cannot recover
from. v3.6.0's gogo code had no bound, and this fork added one; protobuf
bounds the recursion itself (`proto.UnmarshalOptions.RecursionLimit`,
10,000 levels by default), so the fork's bound (`MaxMessageNesting`,
`ErrNestingTooDeep`) is gone. A transport can set a lower limit; raft nests
one level, and peers send none. Tests: `TestNestingLimit`,
`TestNestingCannotExhaustStack`.

**Decoding cost.** Small encodings expand in memory: an empty `Message` in
`Responses` is 2 bytes on the wire and a whole struct in memory, and every
scalar field is an allocation behind its pointer.
`TestDecodeAmplification` measures the worst shapes so that a transport
can set its message size limit: at most about 127 bytes allocated per input
byte (empty `Responses`; 70 for empty `Entries`), counting outgrown slices.
v3.6.0's gogo code allocated up to about 490.

## Platforms

The fork refused 32-bit platforms, because v3.6.0's generated decoder
accumulated field lengths in an `int`, so that a crafted length could wrap
around on 32 bits. protobuf's decoder does not, and the fork builds and
passes its tests on 32-bit platforms again; CI runs them with `GOARCH=386`.

## Additions to the API

- `Config.ElectionRand`: the source of election-timeout jitter, for
  deterministic simulation. When nil, the default is unchanged.
- `ValidateMessage`, `ErrInvalidMessage`: see above.
- `ValidateConfChange(cs, cc)`: whether `ApplyConfChange` can apply `cc` to
  `cs` (a nil `cs` is an empty configuration). An application can treat a
  committed change that fails this check as a no-op on every node.

## Contracts for applications

These held upstream too, but upstream did not spell them all out. The
simulator relies on them.

- **Storage.** On restart, `InitialState` must report a commit index of at
  least the snapshot index, even if a crash kept a snapshot and lost the
  hard state saved with it.
- **Membership.** Shut down a removed node only after every voter of the new
  configuration has applied its removal. Until then, they may need its vote.
- **Transport.** Authenticate `From` as described above. Bound message
  sizes, with the amplification factors above in mind, and consider a
  lower `RecursionLimit` when decoding.
- **Messages and entries are shared.** `Step` keeps the message it is
  given (a leader holds pending reads, for example), and the entries and
  messages in a `Ready` are raft's own: do not modify any of them
  afterwards. With values this was mostly harmless; with pointers, a change
  reaches raft's log.
- **`DisableConfChangeValidation`.** Configuration changes must then be
  serialized above raft. Wait for each change to be applied by every member
  before proposing the next one; the commit inference above is off in this
  mode.
